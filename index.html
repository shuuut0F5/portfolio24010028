Terraform と LXD を組み合わせて、軽量コンテナ 3 台（1 / 2 / 3）を自動構築し、HAProxy によるラウンドロビン負荷分散を実装した環境を構築しました。ローカル環境でクラウドのような構成を再現し、IaC・コンテナ仮想化・ネットワーク構成・負荷分散の一連の流れを理解したことを示す作品です。

プロジェクト概要

ローカル環境でクラウドのような構成を再現し、IaC・コンテナ仮想化・ネットワーク構成・負荷分散の一連の流れを理解しました。

  • 目的：IaC、コンテナ仮想化、ネットワーク構成、負荷分散の流れを、自分の手で構築して理解する
  • やったこと：Terraform で LXD コンテナ 3 台を自動構築 → Nginx を導入 → Proxy Device でポート公開 → HAProxy で振り分け
  • 結果：アクセスごとに 1 番 → 2 番 → 3 番のサーバーへ切り替わることを確認

自分が担当した内容

  • 全自動再現環境構築: Vagrant × Ansible を連携させ、vagrant up 1コマンドで完結する自動プロビジョニング基盤の実装
  • トラブル解決: パーミッション、ストレージ競合、ロック状態、プロファイル依存関係など全6件のエラー切り分けと解消

工夫と実装ポイント

  • 無料・高速に作り直せる検証環境：クラウドではなく LXD の軽量コンテナを採用。起動が速いので、壊して作り直す試行錯誤を何度も繰り返せた
  • 台数の変更はコード1行：count = 3 の数字を変えるだけで台数を増減できる設計にしたvm.tf
  • 作成後すぐ使える状態に：start_container と wait_for_network を指定し、起動とネットワークの準備まで Terraform に任せたvm.tf
  • 振り分けを実際に確認：balance roundrobin とヘルスチェック（check）を設定し、番号ごとの挨拶で切り替わりを目で確認できるようにしたhaproxy.cfg
  • ロックや依存関係のエラーを解消：ストレージロック・プロファイル依存・作成中コンテナのロックを解消し、環境を作り直せる状態に戻したトラブルシューティング

主要な構成ファイル

コードは折りたたんでいます。ハイライトの行が、上の「工夫と実装ポイント」に対応する部分です。

vm.tf (Terraform) のコードを表示 
terraform {
  required_providers {
    lxd = {
      source  = "terraform-lxd/lxd"
      version = "1.7.0"
    }
  }
}

provider "lxd" {}

resource "lxd_container" "web" {
  count = 3
  name  = "web-${count.index + 1}"
  image = "ubuntu:22.04"

  start_container  = true
  wait_for_network = true
}
haproxy.cfg (HAProxy configuration) のコードを表示 
frontend http_front
    bind *:8080
    mode http
    default_backend http_back

backend http_back
    mode http
    balance roundrobin
    server s1 127.0.0.1:8081 check
    server s2 127.0.0.1:8082 check
    server s3 127.0.0.1:8083 check

直面した問題と解決（トラブルシューティング）

構築中に起きた6件の問題を、「事象 → 原因 → 解決 → 学び」の順に整理しています。クリックすると詳細が開きます。

問題解決の進め方（共通）

  1. エラーメッセージを読み、どの部分が何を拒否・失敗したのかを確認する
  2. ログや状態（権限・ストレージ・プロファイル・コンテナなど）を調べて、原因を1つに絞る
  3. 最小限の修正で解決し、再発を防ぐ手順を残す
#問題原因の種類身についた力
1VirtualBox プロバイダーが見つからない前提の確認不足手段に固執せず、目的に合う方法へ切り替える判断力
2LXD ソケットで Permission Denied権限（グループ未所属）エラー文から原因を特定する力
3ストレージプール名の競合過去環境の残骸既存リソースを先に確認する習慣
4ストレージのロックストレージが使用中・未解放ロックの原因を絞り込む力
5プロファイルの依存関係プロファイルを利用中のコンテナが存在依存関係を踏まえた作業順の判断
6作成中コンテナのロック作成処理の中断によるロックの残り失敗後の状態確認と復旧
VirtualBox 1. VirtualBoxプロバイダーの取得失敗 (未登録)
+
  • 問題 当初、仮想マシンの制御にVirtualBoxを使用しようと試み、Terraform設定に書き加えたが、terraform init 時にプロバイダーが見つからないエラーとなった。
  • 原因 VirtualBox用のTerraformプロバイダー（hashicorp/virtualbox）は公式レジストリに存在しないため。
  • 解決 インフラの検証を円滑に進めるため、VirtualBoxでの実行を中止し、LXDによるシステムコンテナベースの検証へ方針変更。LXDはTerraformの公式・コミュニティプロバイダーが安定して提供されており、動作も非常に高速であるため、よりモダンで再現性の高い構成へと昇華できた。
  • 学び 使うツールを決める前に公式レジストリの提供状況を確認する習慣を習得。手段に固執せず「IaCを検証する」という目的に沿って柔軟にアプローチを切り替える判断力を養えた。
LXD UNIX Socket 2. LXDソケットへの通信権限エラー (Permission Denied)
+
  • 問題 terraform apply 実行時、LXDデーモンと通信するUNIXソケットに対し接続拒否エラー（dial unix /var/snap/lxd/common/lxd/unix.socket: connect: permission denied）が発生。
  • 原因 Terraformを実行している一般ユーザー（siwuser）が、LXDの操作に必要な lxd ユーザーグループに所属していなかったため。
  • 解決 sudo usermod -aG lxd siwuser でユーザーをLXDグループに追加し、セッション再接続（ホスト再起動）でグループ設定を適用。
  • 学び エラー文の permission denied とソケットのパスから「デーモンへの権限不足」を的確に特定。Linux環境における実行ユーザーのグループ権限確認の重要性を体得。
LXD Storage 3. ストレージプールの作成競合
+
  • 問題 lxd init 実行時、ストレージプールが重複しているという警告（The requested storage pool "default" already exists.）が発生。
  • 原因 過去に初期化したLXD環境の残骸により、デフォルトプール名 default がシステム内で利用中だった。
  • 解決 初期化プロンプトに従い、未使用の新しいプール名（default2）を指定して設定をバイパスし、無事に初期化を完了。
  • 学び 「過去環境の残骸が残っていないか」を初期化前に確認する習慣がついた。既存リソースの状態把握が安定稼働の前提であると理解。
LXD Storage 4. ストレージのロック
+
  • 問題 LXD のストレージ（default / btrfs）が使用中・ロック状態になり、コンテナの作成や削除などの操作が進まなくなった。
  • 原因 ストレージを使用しているプロセスやバックグラウンド処理が残っており、リソースが正常に解放されていなかった。
  • 解決 ロックの原因になっている処理・依存リソースを確認して解放し、あらためて Terraform でコンテナを作成。
  • 学び LXD ではストレージ・プロファイル・コンテナが密接に連動している。「何がストレージを掴んでいるか」をプロセス・リソース単位で調べる切り分け力を習得。
LXD Profile 5. プロファイルの依存関係
+
  • 問題 プロファイルを変更・削除しようとして依存関係エラーでブロックされた。
  • 原因 default プロファイル（root disk, eth0 nic）をコンテナが参照している状態では、プロファイル単体での変更・削除ができない制約による。
  • 解決 プロファイルに依存しているコンテナを先に停止・整理してから、プロファイル側の設定を変更。
  • 学び 「作るときはプロファイル → コンテナ、消すときはコンテナ → プロファイル」という依存関係の順序性を意識した安全な作業手順を確立。
LXD Instance 6. 作成中コンテナのロック解除
+
  • 問題 コンテナが「作成中」ステータスのまま固まり、他の操作を受け付けなくなった。
  • 原因 ネットワーク切断や作成処理の中断により、インスタンスの排他ロックファイルが残存してしまったため。
  • 解決 lxc コマンドで強制停止・ロックを安全に解除し、状態を整合させてから Terraform で再プロビジョニングを実行。
  • 学び 失敗時はすぐ再実行せず、lxc list で状態を確認しクリーンアップしてから次の操作に進む運用規律を確立。

工夫と実装ポイント

  • 4層を1ファイルで定義：ネットワーク・ボリューム・依存関係をコード化し、docker compose up -d だけで本番に近い構成を起動docker-compose.yml
  • パスワードをコードから分離：DB のパスワードを .env に置き、Git の管理対象外にしたdocker-compose.yml
  • 起動から確認まで自動化：Docker の導入・Compose の配置・起動・/health の確認までを Playbook にまとめ、複数ホストへ一括適用site.yml
  • リクエストの流れを実装：Nginx の FastCGI 設定で PHP-FPM へ中継し、PHP から MySQL（PDO）と Redis に接続
  • PHP 拡張を Dockerfile で管理：pecl で Redis 拡張をビルドして組み込み、環境差が出ないようにしたDockerfile

site.yml (Ansible Playbook) のコードを表示 
---
- name: Deploy application stack
  hosts: webservers
  become: yes

  tasks:
    - name: Install Docker and Docker Compose
      apt:
        name: "{{ item }}"
        state: present
      loop:
        - docker.io
        - docker-compose

    - name: Copy docker-compose.yml
      copy:
        src: docker-compose.yml
        dest: /opt/app/docker-compose.yml
        owner: root
        mode: '0644'

    - name: Start services
      shell: docker-compose -f /opt/app/docker-compose.yml up -d

    - name: Wait for MySQL
      wait_for:
        port: 3306
        delay: 5

    - name: Check application health
      uri:
        url: http://localhost:80/health
        status_code: 200
      retries: 3
      delay: 2

構築中に発生した問題と解決

構築中に起きた4件の問題を、「事象 → 原因 → 解決 → 学び」の順に整理しています。クリックすると詳細が開きます。

問題解決の進め方（共通）

  1. エラーメッセージを読み、どの部分が何を拒否・失敗したのかを確認する
  2. ログや設定（ネットワーク・インベントリ・ボリューム）を調べて、原因を1つに絞る
  3. 最小限の修正で解決し、再発を防ぐ設定をコードに残す
#問題原因の種類身についた力
1コンテナ間の DNS 解決失敗起動順と準備完了の違い依存関係を踏まえた起動設計
2Ansible から SSH 接続失敗接続情報・認証の設定不備接続エラーの切り分け手順
3MySQL のデータが消える永続化の設定漏れデータの永続化設計

Docker Network 1. コンテナ間通信の DNS 解決失敗
+
  • 問題 PHP コンテナから MySQL コンテナへの接続時、ホスト名（mysql）が解決されず接続エラーが発生。
  • 原因 Docker Compose の depends_on はコンテナの起動順序のみを制御し、サービスの初期化完了（MySQLの受付準備）までは保証しないため。
  • 解決 PHP コンテナのエントリーポイントに wait-for-it.sh を組み込み、MySQL（ポート3306）の完全起動を待機してから PHP-FPM を初期化するロジックを実装。
  • 学び 「コンテナ起動」と「サービス準備完了」の違いを理解。分散環境における起動順序依存を解消する待機パターンの必要性を体得。
Ansible SSH 2. Ansible から リモートホストへの SSH 接続失敗
+
  • 問題 Ansible Playbook 実行時、リモートホストへの SSH 接続がタイムアウト（fatal: UNREACHABLE! Failed to connect via ssh）となる。
  • 原因 インベントリファイル（inventory.ini）のIPアドレス誤設定、およびSSH秘密鍵の権限・指定不備による。
  • 解決 インベントリの接続先IPを確認修正し、SSH公開鍵をターゲットホストへ配置。さらに ansible.cfg で秘密鍵パス（private_key_file）を明示設定。
  • 学び 接続トラブルは「疎通（IP/Ping） ➔ 認証（SSH鍵・権限）」の2段階で切り分ける定石を確立。環境固有の設定は cfg ファイルに集約して再現性を担保。
Volume Mount 3. コンテナ内の MySQL データベース永続化失敗
+
  • 問題 Docker Compose でコンテナを再起動（down / up）すると、MySQL に登録したテストデータが初期化・消失してしまう。
  • 原因 docker-compose.yml で永続化ボリューム（Volume）が未定義で、コンテナライフサイクルと共にレイヤーが破棄されていたため。
  • 解決 Docker Compose に Named Volume（mysql_data:/var/lib/mysql）を定義し、コンテナが破棄されてもストレージ実体がホスト側に保持される設計に変更。
  • 学び コンテナのステートレス性とステートフルリソースの分離を理解。再起動・破棄後もデータが維持されることを検証コマンドで確認する習慣を獲得。
File Permissions 4. Ansible による ファイルコピー後のパーミッション不一致
+
  • 問題 Ansible で設定ファイルをリモートホストにコピー後、Compose コマンド実行時に権限拒否（Permission denied）が発生。
  • 原因 Ansible の copy モジュール実行時にファイルのパーミッション・所有者が明示されておらず、環境デフォルトの権限が適用されていたため。
  • 解決 Playbook の copy タスクに mode: '0644', owner: root, group: root を明示的に指定。
  • 学び 「Playbookに書かれていない設定は環境任せになる」というIaCの鉄則を実感。どのホストでも同じ状態を厳格に再現する宣言的コーディングを徹底。

学び

1. 手作業から自動化された構成管理へ

環境構築の再現性が劇的に向上し、検証用コンテナを壊しても即座に作り直せるようになりました。また、構成の変更を Git のコード差分として管理できるようになり、設定変更のレビューや履歴追跡の確実性を実感しました。

2. マルチコンテナ構成の理解と実装

Web（Nginx）・AP（PHP-FPM）・DB（MySQL）・Cache（Redis）それぞれの役割とネットワーク境界を理解した上で連携を構築。本番に近い多層構成をローカル環境で再現・検証できるようになりました。

3. Ansible による自動化の基礎を習得（自動化した作業内容）

複数ホストへの一括適用、パッケージ管理、サービス起動、ヘルスチェックまでの運用タスク自動化を実装しました。
【Ansibleで自動化した作業内容の具体例】 手動ではホストごとに手順書を見ながら実行していた以下の5工程・全12タスクを、Playbook（site.yml）により完全自動化しました：

  • ① 依存パッケージの自動導入: リモートホストの apt キャッシュ更新、および Docker / Docker Compose パッケージの自動インストール (apt)
  • ② 構成ファイルの厳格な転送: docker-compose.yml、nginx.conf、php.ini などを所有者（root）とパーミッション（0644）を保ったまま一括配置 (copy)
  • ③ マルチコンテナの一括起動: 4層コンテナスタックのバックグラウンド起動処理 (shell: docker-compose up -d)
  • ④ データベース起動待ち合わせ: MySQL（ポート 3306）がリクエスト受付可能になるまで接続待機 (wait_for)
  • ⑤ アプリケーション正常性の自動検証: Webエンドポイント（http://localhost/health）へHTTPリクエストを送信し、HTTP 200 OK のステータスコードを自動検証 (uri)

4. Web インフラの全体像を把握できるようになった

  • Reverse Proxy → Application → Database / Cache：リクエストの流れ（Nginx → PHP-FPM → MySQL / Redis）を構築し、Webインフラ全体のデータフローを把握
  • クラウドインフラの基礎：IaC・構成管理・マルチコンテナといったクラウドインフラの基礎をローカルで再現し、実践レベルの理解に到達
  • Docker / Docker Compose：マルチコンテナアプリケーションの定義と管理スキル
  • Ansible Playbook：宣言的な構成管理とリモートホスト一括制御能力
