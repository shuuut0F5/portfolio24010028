Terraform × LXD による軽量コンテナ環境構築（3台構成 + 負荷分散）

Terraform と LXD を組み合わせて、軽量コンテナ 3 台（1 / 2 / 3）を自動構築し、HAProxy によるラウンドロビン負荷分散を実装した環境を構築しました。ローカル環境でクラウドのような構成を再現し、IaC・コンテナ仮想化・ネットワーク構成・負荷分散の一連の流れを理解したことを示す作品です。

主要技術

Terraform / LXD

インフラ規模

3 Web Nodes

分散アルゴリズム

Round Robin

環境

Ubuntu（VirtualBox） LXD Terraform HAProxy Nginx

動作結果

検証済み

ロードバランサー（localhost:8080）にアクセスするたびに、1番 → 2番 → 3番のサーバーへ切り替わります。

$ curl http://localhost:8080

Good evening, this is server 3.
  • 構築：terraform apply で web-1〜web-3 の3コンテナが自動生成された
  • 分散：balance roundrobin の設定どおり、アクセスごとに 1 → 2 → 3 と切り替わった

プロジェクト概要

ローカル環境でクラウドのような構成を再現し、IaC・コンテナ仮想化・ネットワーク構成・負荷分散の一連の流れを理解しました。

  • 目的：IaC、コンテナ仮想化、ネットワーク構成、負荷分散の流れを、自分の手で構築して理解する
  • やったこと：Terraform で LXD コンテナ 3 台を自動構築 → Nginx を導入 → Proxy Device でポート公開 → HAProxy で振り分け
  • 結果：アクセスごとに 1 番 → 2 番 → 3 番のサーバーへ切り替わることを確認

工夫と実装ポイント

  • 無料・高速に作り直せる検証環境：クラウドではなく LXD の軽量コンテナを採用。起動が速いので、壊して作り直す試行錯誤を何度も繰り返せた
  • 台数の変更はコード1行：count = 3 の数字を変えるだけで台数を増減できる設計にしたvm.tf
  • 作成後すぐ使える状態に：start_container と wait_for_network を指定し、起動とネットワークの準備まで Terraform に任せたvm.tf
  • 振り分けを実際に確認：balance roundrobin とヘルスチェック（check）を設定し、番号ごとの挨拶で切り替わりを目で確認できるようにしたhaproxy.cfg
  • ロックや依存関係のエラーを解消：ストレージロック・プロファイル依存・作成中コンテナのロックを解消し、環境を作り直せる状態に戻したトラブルシューティング

主要な構成ファイル

コードは折りたたんでいます。ハイライトの行が、上の「工夫と実装ポイント」に対応する部分です。

vm.tf (Terraform) のコードを表示 
terraform {
  required_providers {
    lxd = {
      source  = "terraform-lxd/lxd"
      version = "1.7.0"
    }
  }
}

provider "lxd" {}

resource "lxd_container" "web" {
  count = 3
  name  = "web-${count.index + 1}"
  image = "ubuntu:22.04"

  start_container  = true
  wait_for_network = true
}
haproxy.cfg (HAProxy configuration) のコードを表示 
frontend http_front
    bind *:8080
    mode http
    default_backend http_back

backend http_back
    mode http
    balance roundrobin
    server s1 127.0.0.1:8081 check
    server s2 127.0.0.1:8082 check
    server s3 127.0.0.1:8083 check

VirtualBox 1. VirtualBoxプロバイダーの取得失敗 (未登録)
+

【事象】
当初、仮想マシンの制御にVirtualBoxを使用しようと試み、Terraform設定に書き加えたが、terraform init時にプロバイダーが見つからないエラーとなった。

【原因】
VirtualBox用のTerraformプロバイダー（hashicorp/virtualbox）は公式レジストリに存在しないため。

【解決策】
インフラの検証を円滑に進めるため、VirtualBoxでの実行を中止し、LXDによるシステムコンテナベースの検証へ方針変更。LXDはTerraformの公式・コミュニティプロバイダーが安定して提供されており、動作も非常に高速であるため、よりモダンで再現性の高い構成へと昇華できた。

【学び】
使うツールを決める前に、公式レジストリにプロバイダーがあるかを確認する。行き詰まったら手段に固執せず、「IaC を検証する」という目的に合う別の方法へ切り替える判断が大事だと学んだ。

LXD UNIX Socket 2. LXDソケットへの通信権限エラー (Permission Denied)
+

【事象】
terraform apply 時に、LXDデーモンと通信するUNIXソケットに対し、接続拒否エラーが発生。
dial unix /var/snap/lxd/common/lxd/unix.socket: connect: permission denied

【原因】
Terraformを実行している一般ユーザー（siwuser）が、LXDの操作に必要な lxd ユーザーグループに所属していなかったため。

【解決策】
ユーザーをLXDグループに追加するコマンドを実行し、ホスト環境を再起動させてグループ設定を適用。 

sudo usermod -aG lxd siwuser
sudo reboot

【学び】
エラー文の permission denied とソケットのパスから、「デーモンへの権限不足」だと切り分けられた。操作系ツールでは、実行ユーザーが必要なグループに入っているかの確認が基本。

LXD Storage 3. ストレージプールの作成競合
+

【事象】
lxd init 実行時、ストレージプールが重複しているという警告が発生。
The requested storage pool "default" already exists. Please choose another name.

【原因】
過去に初期化したLXD環境の残骸により、デフォルトのストレージプール名である default がシステム内で利用中だった。

【解決策】
初期化プロンプトに従い、未使用の新しいプール名（例: default2）を入力して設定をバイパスし、無事に初期化を完了させた。

【学び】
「過去の環境の残骸が残っていないか」を最初に確認する習慣がついた。既存のプール名を確認してから初期化すれば、同じ警告は防げる。

LXD Storage 4. ストレージのロック
+

【事象】
LXD のストレージ（default / btrfs）が使用中・ロック状態になり、コンテナの作成や削除などの操作が進まなくなった。

【原因】
ストレージを使っている処理やリソースが残っており、ストレージが解放されていなかった。

【解決策】
ロックの原因になっている処理・リソースを確認して解消し、あらためて Terraform でコンテナを作成した。

【学び】
LXD ではストレージ・プロファイル・コンテナが互いに関係している。操作の前に「何がそのストレージを使っているか」を確認すると、ロックの原因を絞り込める。

LXD Profile 5. プロファイルの依存関係
+

【事象】
プロファイルを変更・削除しようとして、エラーで止まった。

【原因】
default プロファイル（root の disk と eth0 の nic）は、コンテナから利用されている。利用中のコンテナがあると、プロファイルだけを単独では操作できない。

【解決策】
プロファイルに依存しているコンテナを先に整理してから、プロファイルを操作した。

【学び】
作るときは「プロファイル → コンテナ」、消すときはその逆の順になる。依存関係を意識して、作業の順番を決める習慣がついた。

LXD Instance 6. 作成中コンテナのロック解除
+

【事象】
コンテナが「作成中」の状態のまま、他の操作を受け付けなくなった。

【原因】
作成処理が途中で止まり、ロックが残ってしまった。

【解決策】
作成中のコンテナのロックを解除し、状態を整えてから Terraform で作り直した。

【学び】
失敗した処理のあとは、コンテナの状態（lxc list）を確認してから次の操作に進む。中途半端な状態を残さないことが、再現できる環境づくりにつながる。

学び

1. 手作業インフラ構築から、再現性の高いIaCへ

物理環境の構築・設定のすべてを手動で行っていた手法を脱却し、インフラを「コード（HCL）」で定義することで、誰が実行しても同じ環境を秒単位で再現できる強みを体験しました。これにより、開発環境のスクラップ＆ビルドが容易になりました。

2. スケールアウトの概念理解

Terraformのメタ引数である count を変更するだけで、1台のWebサーバーから3台、あるいはそれ以上へと瞬時にスケールアウトできる設計方法を学びました。これはAWS等のAuto Scalingや冗長化の根本原理を掴むのに大きく貢献しました。

3. ネットワークトラフィック制御とポート設計

LXDのプロキシ設定を通じ、仮想内部ネットワークと外部ホストの通信経路を設計しました。また、ロードバランサー（HAProxy）によるレイヤー4/7の中継処理と、クライアントからのリクエストが均等に分散されていくラウンドロビンの動向を検証レベルで実証しました。

4. LXDの構成と依存関係の理解

lxdbr0（bridge）＋ IPv4 NAT、default ストレージ（btrfs）、default プロファイルの root（disk）と eth0（nic）といった LXD の基本構成を理解しました。ストレージのロックやプロファイルの依存関係、作成中コンテナのロックなどのトラブルを通じて、リソース同士の依存関係を意識して操作する大切さを学びました。

5. プロジェクト達成による技術スキル成長

  • インフラコード化能力: Terraformを用いた宣言的コード開発スキルの獲得

Nginx・PHP-FPM・MySQL・Redis の4層構成を Docker Compose で定義し、Ansible で自動デプロイしたプロジェクトです。

検証済み

コンテナの起動から、Ansible による複数ホストへの自動デプロイ、/health の自動チェックまでを確認しました。

# 確認に使ったコマンド

  • 永続化：コンテナを再起動しても、MySQL のデータが保持されることを確認した

プロジェクト概要

Docker Compose で Web・アプリ・DB・キャッシュの4層を定義し、Ansible で複数ホストへ自動デプロイするところまでを、ローカルで再現しました。

  • 目的：本番に近い構成を、誰がやっても同じ手順で再現できる形にする
  • やったこと：Compose で4コンテナを定義 → Ansible の Playbook で Docker の導入・ファイル配置・起動・ヘルスチェックまで自動化
  • 結果：docker compose up -d と ansible-playbook の2つのコマンドで構成を再現
  • 補足：この作品は負荷分散ではなく、役割ごとにコンテナを分ける「多層構成」とデプロイ自動化が主題です（負荷分散は Terraform × LXD の作品で実装）

※ この構成は負荷分散ではなく、役割ごとにコンテナを分けた多層構成です。Nginx はリクエストを PHP-FPM へ中継（リバースプロキシ）し、PHP が MySQL（データ）と Redis（キャッシュ）にアクセスします。ラウンドロビンによる負荷分散は、Terraform × LXD の作品で実装しています。

工夫と実装ポイント

  • 4層を1ファイルで定義：ネットワーク・ボリューム・依存関係をコード化し、docker compose up -d だけで本番に近い構成を起動docker-compose.yml
  • パスワードをコードから分離：DB のパスワードを .env に置き、Git の管理対象外にしたdocker-compose.yml
  • 起動から確認まで自動化：Docker の導入・Compose の配置・起動・/health の確認までを Playbook にまとめ、複数ホストへ一括適用site.yml
  • リクエストの流れを実装：Nginx の FastCGI 設定で PHP-FPM へ中継し、PHP から MySQL（PDO）と Redis に接続
  • PHP 拡張を Dockerfile で管理：pecl で Redis 拡張をビルドして組み込み、環境差が出ないようにしたDockerfile

主要な構成ファイル

コードは折りたたんでいます。ハイライトの行が、上の「工夫と実装ポイント」に対応する部分です。

docker-compose.yml のコードを表示 
version: '3.8'

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./app:/var/www/html:ro
    depends_on:
      - php-fpm
    networks:
      - app-network

  php-fpm:
    build:
      context: ./php
      dockerfile: Dockerfile
    volumes:
      - ./app:/var/www/html
    environment:
      - DB_HOST=mysql
      - CACHE_HOST=redis
    depends_on:
      - mysql
      - redis
    networks:
      - app-network

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}  # .env から読み込む
      MYSQL_DATABASE: appdb
    volumes:
      - mysql_data:/var/lib/mysql
    networks:
      - app-network

  redis:
    image: redis:7-alpine
    networks:
      - app-network

volumes:
  mysql_data:

networks:
  app-network:
    driver: bridge

※ DBのパスワードは設定ファイルに直接書かず、.env に分離して読み込む形にしています（.env は Git の管理対象外にします）。

site.yml (Ansible Playbook) のコードを表示 
---
- name: Deploy application stack
  hosts: webservers
  become: yes

  tasks:
    - name: Install Docker and Docker Compose
      apt:
        name: "{{ item }}"
        state: present
      loop:
        - docker.io
        - docker-compose

    - name: Copy docker-compose.yml
      copy:
        src: docker-compose.yml
        dest: /opt/app/docker-compose.yml
        owner: root
        mode: '0644'

    - name: Start services
      shell: docker-compose -f /opt/app/docker-compose.yml up -d

    - name: Wait for MySQL
      wait_for:
        port: 3306
        delay: 5

    - name: Check application health
      uri:
        url: http://localhost:80/health
        status_code: 200
      retries: 3
      delay: 2
Dockerfile (PHP拡張ビルド) のコードを表示 
FROM php:8.2-fpm
RUN apt-get update && apt-get install -y libssl-dev \
    && pecl install redis \
    && docker-php-ext-enable redis

Docker Network 1. コンテナ間通信の DNS 解決失敗
+

【事象】
PHP コンテナから MySQL コンテナへの接続時、ホスト名（mysql）が解決されず、接続エラーが発生。

【原因】
Docker Compose のデフォルトネットワークでは、サービス名による自動 DNS 解決が行われますが、depends_on は起動順序のみを制御し、サービスの「完全な起動」は保証しません。PHP が起動時に MySQL へ接続したが、MySQL がまだ初期化中の可能性がありました。

【解決策】
PHP コンテナのエントリーポイントスクリプトに、wait-for-it.sh を用いた MySQL への接続待機ロジックを追加。これにより、MySQL が完全に起動してから PHP アプリケーションが初期化されるようになりました。 

./wait-for-it.sh mysql:3306 -t 30 -- php-fpm

【学び】
depends_on は「起動順」だけを制御し、「準備完了」までは保証しないと理解した。待機処理（wait-for-it）を入れ、起動順の問題を吸収する設計にした。

Ansible SSH 2. Ansible から リモートホストへの SSH 接続失敗
+

【事象】
Ansible プレイブック実行時、リモートホストへの SSH 接続がタイムアウト。
fatal: [deploy-host-1]: UNREACHABLE! => {msg: 'Failed to connect to the host via ssh'}

【原因】
インベントリファイルで指定した IP アドレスが誤っていた、また SSH キー認証の設定が不完全だった。

【解決策】
インベントリファイルの IP アドレスを再確認し、SSH 公開鍵をリモートホストに配置。また、ansible.cfg で SSH パラメータを明示的に設定しました。 

[defaults]
host_key_checking = False
private_key_file = ~/.ssh/id_rsa

ansible-playbook -i inventory.ini site.yml

【学び】
接続エラーは「IP アドレス → 鍵認証」の順に切り分ける。設定は ansible.cfg に明示して再現性を確保した。なお host_key_checking = False は検証環境向けの設定で、本番では known_hosts で検証する必要がある。

Volume Mount 3. コンテナ内の MySQL データベース永続化失敗
+

【事象】
Docker Compose でコンテナを再起動すると、MySQL データベースのデータが初期化されてしまう。

【原因】
docker-compose.yml で MySQL のボリュームマウントが未定義か、正しく設定されていなかった。

【解決策】
Docker Compose の volumes セクションで Named Volume を定義し、MySQL コンテナをマウント。これにより、コンテナの再起動後もデータが保持されるようになりました。 

volumes:
  mysql_data:

services:
  mysql:
    volumes:
      - mysql_data:/var/lib/mysql

【学び】
コンテナは破棄されるとデータも消える。残したいデータは Named Volume に置き、再起動してもデータが残るかを実際に確認して検証した。

File Permissions 4. Ansible による ファイルコピー後のパーミッション不一致
+

【事象】
Ansible で docker-compose.yml をリモートホストにコピー後、Docker Compose コマンド実行時にパーミッション拒除エラーが発生。

【原因】
Ansible の copy モジュール実行時に、ファイルのパーミッション設定が明示的に指定されていなかった。

【解決策】
Ansible プレイブックの copy タスクに、mode パラメータを追加してファイルパーミッションを明示的に設定。 

- name: Copy docker-compose.yml
  copy:
    src: docker-compose.yml
    dest: /opt/app/docker-compose.yml
    owner: root
    group: root
    mode: '0644'

【学び】
mode や owner を明示すると、どのホストでも同じ状態になる。Playbook は「書いていないことは環境任せになる」ことを意識して書くようになった。
