Terraform × LXD Web Infrastructure

完全無料のローカルコンテナ環境を用いた、複数Webサーバーとロードバランサーによる高可用性インフラ構築プロジェクト

主要技術

Terraform / LXD

インフラ規模

3 Web Nodes

分散アルゴリズム

Round Robin

検証済みスタック

LXD Ubuntu Nginx HAProxy

プロジェクト概要

本プロジェクトは、インフラの構築手順をコードで定義する Infrastructure as Code (IaC) をローカルPC上で高速に、かつ完全に無料の枠組みで体験・実証するために構成されました。

一般的に検証コストが掛かりやすいパブリッククラウド（AWSなど）を用いることなく、Linux標準のシステムコンテナ管理システムである LXD をバックエンドに採用。Terraform経由で複数のUbuntu仮想インスタンスを秒単位で瞬時に構築・破壊できる再現性の高い実証基盤を作り上げ、さらにHAProxyによるWebトラフィックの動的ロードバランシングまでを検証しています。

システムネットワーク構成図
Client User
HTTP: localhost:8080
HAProxy (Load Balancer)
Port 8080 ➔ Round Robin
web-1
Ubuntu 22.04 | Nginx
Port 8081 (Proxy)
web-2
Ubuntu 22.04 | Nginx

web-3
Ubuntu 22.04 | Nginx

工夫と実装ポイント

  • 完全無料でのクラウド検証環境実現：AWSなどの商用クラウドを使わず、LXDコンテナのみで複数VM構成を構築。秒単位の高速起動により、試行錯誤が容易
  • Terraform による宣言的インフラ定義：count メタ引数を使い、3台のWebサーバーをパラメータ1つで制御。スケール変更がコード1行で実現可能
  • ラウンドロビン分散の実装検証：HAProxyの設定により、クライアントリクエストが自動的に3台へと均等に分散される動作を実証
  • エラードリフト管理とState管理の習得：Terraform State の重要性を実体験。リソースの競合解決とロールバック技術を確立

主要な構成ファイル

インフラの「宣言的な定義」と「ロードバランサー」の設計構成コードです。

vm.tf (Terraform)

terraform {
  required_providers {
    lxd = {
      source  = "terraform-lxd/lxd"
      version = "1.7.0"
    }
  }
}

provider "lxd" {}

resource "lxd_container" "web" {
  count = 3

  name  = "web-${count.index + 1}"
  image = "ubuntu:22.04"
}

haproxy.cfg (HAProxy configuration)

frontend http_front
    bind *:8080
    mode http
    default_backend http_back

backend http_back
    mode http
    balance roundrobin
    server web1 127.0.0.1:8081 check
    server web2 127.0.0.1:8082 check
    server web3 127.0.0.1:8083 check

インフラ構築ステップ

初期の基盤導入から、複数コンテナの自動作成、ロードバランサー連携までの構築手順です。

Success

1. LXD インフラ環境のインストールと初期化

ホストマシンにLXDシステムを導入。コンテナ仮想化により、通常の重たい仮想マシンの起動を数秒の軽量コンテナ起動に代替し、完全無料・超高速な検証体制を構築。 

sudo apt update

sudo lxd init
Success

インフラ構成定義ファイル vm.tf を作成。複数インスタンス構成を count = 3 パラメータで宣言的にコード定義し、一括で構築。 

terraform init
terraform apply
Success

3. nginx のインストール（コンテナ内部）

構築したコンテナにログインし、Webサーバー（Nginx）を個別にインストールします。

# コンテナ内部で実行
sudo apt update
sudo apt install -y nginx
Success

4. Web コンテンツの変更による動作確認

各コンテナで異なるメッセージを返すようにインデックスHTMLを書き換え、どのサーバーにアクセスしているか判別できるようにします。

# web-2 コンテナ内
echo "This is web-2" | sudo tee /var/www/html/index.html

# web-3 コンテナ内
echo "This is web-3" | sudo tee /var/www/html/index.html
Success

5. ホストから各コンテナへのポートフォワード設定

LXDの仮想ネットワーク上のコンテナとホスト側ネットワークを接続するため、プロキシポートマッピングを追加。

lxc config device add web-2 http proxy listen=tcp:0.0.0.0:8082 connect=tcp:127.0.0.1:80
lxc config device add web-3 http proxy listen=tcp:0.0.0.0:8083 connect=tcp:127.0.0.1:80
Success

ホスト側にHAProxyを起動し、ラウンドロビンで負荷を分散するよう設定。curl を使って交互に各コンテナへとアクセスが振り分けられることを確認。 

curl http://localhost:8080
# ➔ Output 1: This is web-1
# ➔ Output 2: This is web-2
# ➔ Output 3: This is web-3

直面した問題と解決（トラブルシューティング）

構築の過程で発生した様々なエラーに対し、ログの解析や権限・状態管理（State）の修復を行った問題解決の記録です。クリックすると詳細が開きます。

VirtualBox 1. VirtualBoxプロバイダーの取得失敗 (未登録)
+

【事象】
当初、仮想マシンの制御にVirtualBoxを使用しようと試み、Terraform設定に書き加えたが、terraform init時にプロバイダーが見つからないエラーとなった。

【原因】
VirtualBox用のTerraformプロバイダー（hashicorp/virtualbox）は公式レジストリに存在しないため。

【解決策】
インフラの検証を円滑に進めるため、VirtualBoxでの実行を中止し、**LXDによるシステムコンテナベースの検証へ方針変更**。LXDはTerraformの公式・コミュニティプロバイダーが安定して提供されており、動作も非常に高速であるため、よりモダンで再現性の高い構成へと昇華できた。

LXD UNIX Socket 2. LXDソケットへの通信権限エラー (Permission Denied)
+

【事象】
terraform apply 時に、LXDデーモンと通信するUNIXソケットに対し、接続拒否エラーが発生。
dial unix /var/snap/lxd/common/lxd/unix.socket: connect: permission denied

【原因】
Terraformを実行している一般ユーザー（siwuser）が、LXDの操作に必要な lxd ユーザーグループに所属していなかったため。

【解決策】
ユーザーをLXDグループに追加するコマンドを実行し、ホスト環境を再起動させてグループ設定を適用。

sudo usermod -aG lxd siwuser
sudo reboot

Terraform State 3. コンテナの重複作成・適用競合
+

【事象】
構成適用中に、対象コンテナが既に存在しているとアラートが出現し、実行が停止。
This "instances" entry already exists

【原因】
Terraformを介さずLXD側で直接コンテナを操作した、または前回の不完全な破壊処理などにより、LXDに実機が残っているにも関わらずTerraformの状態管理ファイル（State）には反映されていない「状態の乖離（ドリフト）」が起きていた。

【解決策】
実機側に残っている競合コンテナを強制削除した上で、TerraformのStateから対象のリソース状態を完全にクリアすることで、次回適用時の競合を解消。

lxc delete terraform-test --force
terraform state rm lxd_container.test

LXD Storage 4. ストレージプールの作成競合
+

【事象】
lxd init 実行時、ストレージプールが重複しているという警告が発生。
The requested storage pool "default" already exists. Please choose another name.

【原因】
過去に初期化したLXD環境の残骸により、デフォルトのストレージプール名である default がシステム内で利用中だった。

【解決策】
初期化プロンプトに従い、未使用の新しいプール名（例: default2）を入力して設定をバイパスし、無事に初期化を完了させた。

プロジェクト概要

本プロジェクトでは、Docker Compose と Ansible を組み合わせて、Web サーバー・アプリケーションサーバー・データベース・キャッシュサーバーからなるマルチコンテナ Web インフラを構築しました。開発環境から本番環境へのデプロイまでを自動化し、構成管理ツールによる統一的な運用フローを実証しています。

Ansible のプレイブックを用いて、Docker のインストール・Compose の配置・サービス起動までを自動化。複数ホストへの横展開が可能な構成管理フローを実装し、本番運用で使われる「構成の再現性」「自動化」「一括適用」を体験しました。

工夫と実装ポイント

  • Docker Compose によるマルチコンテナ構成のコード化：Web・アプリ・DB・キャッシュの4コンテナをComposeで一括管理。コンテナ間ネットワーク、ボリューム永続化、依存関係をコード化し、docker compose up -d だけで本番に近い構成を自動構築
  • Ansible による構成管理・自動デプロイ：Docker のインストール、Compose の配置、サービス起動をAnsibleで自動化。複数ホストへの横展開が可能な構成管理フローを実装
  • Nginx → PHP-FPM → MySQL → Redis の連携構築：NginxのFastCGI設定でPHP-FPMにリクエストをルーティングし、PHPからMySQLへPDO接続、RedisキャッシュサーバーとPHPの連携までWebアプリケーションの基本構成をコンテナで完全再現
  • Dockerfile による PHP 拡張のビルド：Redis拡張をpeclでインストールしPHP-FPMに組み込み。本番環境で必要な拡張をDockerfileで管理する方法を習得

主要な構成ファイル

Docker Compose による宣言的なコンテナ定義と、Ansible による構成管理のメイン設定です。

docker-compose.yml

version: '3.8'

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./app:/var/www/html:ro
    depends_on:
      - php-fpm
    networks:
      - app-network

  php-fpm:
    build:
      context: ./php
      dockerfile: Dockerfile
    volumes:
      - ./app:/var/www/html
    environment:
      - DB_HOST=mysql
      - CACHE_HOST=redis
    depends_on:
      - mysql
      - redis
    networks:
      - app-network

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: rootpass
      MYSQL_DATABASE: appdb
    volumes:
      - mysql_data:/var/lib/mysql
    networks:
      - app-network

  redis:
    image: redis:7-alpine
    networks:
      - app-network

volumes:
  mysql_data:

networks:
  app-network:
    driver: bridge

site.yml (Ansible Playbook)

---
- name: Deploy application stack
  hosts: webservers
  become: yes

  tasks:
    - name: Install Docker and Docker Compose
      apt:
        name: "{{ item }}"
        state: present
      loop:
        - docker.io
        - docker-compose

    - name: Copy docker-compose.yml
      copy:
        src: docker-compose.yml
        dest: /opt/app/docker-compose.yml
        owner: root
        mode: '0644'

    - name: Start services
      shell: docker-compose -f /opt/app/docker-compose.yml up -d

    - name: Wait for MySQL
      wait_for:
        port: 3306
        delay: 5

    - name: Check application health
      uri:
        url: http://localhost:80/health
        status_code: 200
      retries: 3
      delay: 2

Dockerfile (PHP拡張ビルド)

FROM php:8.2-fpm
RUN apt-get update && apt-get install -y libssl-dev \
    && pecl install redis \
    && docker-php-ext-enable redis

構築中に発生した問題と解決

運用環境のデプロイメント検証における実際のトラブルと、その解決方法を記録しています。

Docker Network 1. コンテナ間通信の DNS 解決失敗
+

【事象】
PHP コンテナから MySQL コンテナへの接続時、ホスト名（mysql）が解決されず、接続エラーが発生。

【原因】
Docker Compose のデフォルトネットワークでは、サービス名による自動 DNS 解決が行われますが、depends_on は起動順序のみを制御し、サービスの「完全な起動」は保証しません。PHP が起動時に MySQL へ接続したが、MySQL がまだ初期化中の可能性がありました。

【解決策】
PHP コンテナのエントリーポイントスクリプトに、wait-for-it.sh を用いた MySQL への接続待機ロジックを追加。これにより、MySQL が完全に起動してから PHP アプリケーションが初期化されるようになりました。

./wait-for-it.sh mysql:3306 -t 30 -- php-fpm

Ansible SSH 2. Ansible から リモートホストへの SSH 接続失敗
+

【事象】
Ansible プレイブック実行時、リモートホストへの SSH 接続がタイムアウト。
fatal: [deploy-host-1]: UNREACHABLE! => {msg: 'Failed to connect to the host via ssh'}

【原因】
インベントリファイルで指定した IP アドレスが誤っていた、また SSH キー認証の設定が不完全だった。

【解決策】
インベントリファイルの IP アドレスを再確認し、SSH 公開鍵をリモートホストに配置。また、ansible.cfg で SSH パラメータを明示的に設定しました。

[defaults]
host_key_checking = False
private_key_file = ~/.ssh/id_rsa

ansible-playbook -i inventory.ini site.yml

Volume Mount 3. コンテナ内の MySQL データベース永続化失敗
+

【事象】
Docker Compose でコンテナを再起動すると、MySQL データベースのデータが初期化されてしまう。

【原因】
docker-compose.yml で MySQL のボリュームマウントが未定義か、正しく設定されていなかった。

【解決策】
Docker Compose の volumes セクションで Named Volume を定義し、MySQL コンテナをマウント。これにより、コンテナの再起動後もデータが保持されるようになりました。

volumes:
  mysql_data:

services:
  mysql:
    volumes:
      - mysql_data:/var/lib/mysql

File Permissions 4. Ansible による ファイルコピー後のパーミッション不一致
+

【事象】
Ansible で docker-compose.yml をリモートホストにコピー後、Docker Compose コマンド実行時にパーミッション拒除エラーが発生。

【原因】
Ansible の copy モジュール実行時に、ファイルのパーミッション設定が明示的に指定されていなかった。

【解決策】
Ansible プレイブックの copy タスクに、mode パラメータを追加してファイルパーミッションを明示的に設定。

- name: Copy docker-compose.yml
  copy:
    src: docker-compose.yml
    dest: /opt/app/docker-compose.yml
    owner: root
    group: root
    mode: '0644'

得られた実績と学び

1. 手作業から自動化された構成管理へ

環境構築の再現性が向上し、壊してもすぐ作り直せるようになりました。また、構成の変更をコード差分として管理できるようになり、変更内容の把握と共有が容易になりました。

2. マルチコンテナ構成の理解と実装

Web・アプリ・DB・キャッシュそれぞれの役割を理解した上で連携を構築。本番に近い構成をローカル環境で再現できるようになりました。

3. Ansible による自動化の基礎を習得

複数ホストへの一括適用、パッケージ管理、サービス起動の自動化を実装。運用タスクの自動化を実際に体験し、構成管理の重要性を理解しました。

4. Web インフラの全体像を把握できるようになった

  • Reverse Proxy → Application → Database → Cache：一連のリクエストの流れを構築し、Webインフラ全体のデータフローを把握
  • クラウドインフラの基礎：IaC・構成管理・マルチコンテナといったクラウドインフラの基礎をローカルで再現し、実践レベルの理解に到達
  • Docker / Docker Compose：マルチコンテナアプリケーションの定義と管理スキル
  • Ansible Playbook：宣言的な構成管理とリモートホスト一括制御能力
